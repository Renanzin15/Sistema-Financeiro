> Referência do sistema **como ele é hoje** (atualizado em 10/08/2026, após a fase SaaS — Etapas 23–32).
> Descreve arquitetura, autenticação, modelo de dados, rotas e regras de negócio. Para o histórico das

## 1. Visão geral

App web de finanças pessoais (método **orçamento base zero + caixinhas/envelopes**), agora **multi-usuário
privado**: hospedado na nuvem, cada usuário com seus próprios dados isolados. Cadastro de usuários é manual
(signups desativados no Supabase).

**Stack:**
- **Back-end:** Python + FastAPI.
- **Banco:** Postgres (**Supabase**) na nuvem, OU SQLite local (`financeiro.db`) como fallback de dev — escolhido por variável de ambiente.
- **Front-end:** `index.html` + `styles.css` + `app.js` (HTML/CSS/JS puro, sem framework). Fonte **Inter embutida** (base64) no `styles.css`; ícones **SVG embutidos** no `app.js`; gráfico via **Chart.js (CDN)**.
- **Autenticação:** **Supabase Auth** (e-mail/senha). O back verifica o access_token (JWT **ES256** via JWKS; HS256 como reserva).
- **Hospedagem:** **Render** (puxa do GitHub `Renanzin15/Sistema-Financeiro`, privado).
- **OCR (opcional):** Tesseract + pytesseract + Pillow + PyMuPDF — só funciona onde o binário do Tesseract existir (ver §8).

**Arquivos:**
- `main.py` — back-end (API + acesso ao banco + auth) — ~1900 linhas
- `index.html` / `styles.css` / `app.js` — front-end (separados na Etapa 28 pra facilitar manutenção)
- `requirements.txt` — dependências pip
- `migrar_para_supabase.py` — leva um `financeiro.db` (SQLite) pro Postgres carimbando o `user_id`
- `.env` / `CREDENCIAIS_SUPABASE.local.md` — segredos (**gitignored**, nunca versionar)

**Dependências (pip):** `fastapi`, `uvicorn[standard]`, `bcrypt`, `python-jose[cryptography]`, `pydantic`, `psycopg2-binary` (+ opcionais OCR: `pytesseract`, `Pillow`, `PyMuPDF`).

**Como executar (local):** `python -m uvicorn main:app` → `http://127.0.0.1:8000/`. Sem `.env` roda em SQLite; com `.env` (Supabase) roda em Postgres. A auth sempre é Supabase (precisa de `SUPABASE_URL`/token).

## 2. Arquitetura

```
Navegador (index.html + styles.css + app.js)
   │  1) login e-mail/senha  ──────────────►  Supabase Auth (GoTrue)  → access_token (JWT ES256)
   │  2) Bearer <token> nas chamadas de dados
   ▼
FastAPI (main.py, no Render) ── verifica o token (JWKS) → user_id ──► Postgres (Supabase)
                                 regras + acesso ao banco, TUDO filtrado por user_id
```

- O front chama as rotas via `fetch` (`pedir()` manda `Authorization: Bearer <token>`; em 401 volta pro login).
- **Backend escolhe o banco por env:** se houver `PGHOST` (ou `DATABASE_URL`) → Postgres; senão → SQLite. Um wrapper `_ConexaoPG` faz o psycopg2 se comportar como o sqlite3 e traduz os placeholders `?`→`%s`, então os ~115 `con.execute` do código servem pros dois bancos.
- `GET /`, `/app`, `/styles.css`, `/app.js` respondem com `Cache-Control: no-store`.
- **Convenção monetária:** todo dinheiro em **centavos (inteiro)**; ÷100 só na exibição.

## 3. Autenticação (Supabase Auth) e isolamento

- **Login** é feito no front direto contra o Supabase: `POST {SUPABASE_URL}/auth/v1/token?grant_type=password` (header `apikey` = publishable key, ambos **públicos**, hardcoded no `app.js`). Devolve `access_token`; o front guarda no `localStorage` (não desloga no refresh).
- **Verificação no back (`exigir_login` → `_verificar_token`):** o projeto assina em **ES256** (chave assimétrica publicada no JWKS `/auth/v1/.well-known/jwks.json`). O back busca a chave pública (cacheada, recarrega 1x se rotacionar) e valida ES256; **HS256 com a JWT Secret** fica como reserva/legado. Extrai `sub` = **UUID do usuário** = `user_id`. Sem/ inválido → 401.
- **Isolamento por `user_id`:** **toda** tabela de dados tem `user_id UUID`, e **toda** query filtra/insere por ele (rotas + helpers `saldo_da_caixinha`, `total_conta`, `aplicar_regras_salario`, `gerar_recorrentes_do_mes`, `gerar_entradas_recorrentes`). Ações sobre um id alheio validam posse (`WHERE id=? AND user_id=?` → 404).
- ⚠ **RLS não protege aqui:** o back conecta como role `postgres` (via pooler), que **ignora** o Row Level Security. O isolamento REAL é no código; o RLS fica só como rede de segurança.
- **Novo usuário:** na 1ª vez que acessa, `_garantir_usuario` semeia as categorias padrão dele ("Conta fixa", "Cartão", "Outros"). Não há mais senha única / `senha_hash`.

## 4. Modelo de dados

Postgres: `id BIGINT GENERATED BY DEFAULT AS IDENTITY`. SQLite: `INTEGER PK AUTOINCREMENT`. **Todas** as tabelas de dados têm **`user_id`** (UUID no PG / TEXT no SQLite) + índice por `user_id`.

- **`bancos`** — id, nome, user_id
- **`caixinhas`** — id, nome, banco_id, meta_centavos (0=sem meta), meta_prazo (`AAAA-MM-DD`/NULL), user_id. *(saldo não é coluna — é calculado, §6)*
- **`lancamentos`** — id, tipo (`entrada`/`alocacao`/`pagamento`/`saida_livre`/`rendimento`), valor_centavos, descricao, caixinha_id, data (`AAAA-MM-DD`), user_id
- **`contas`** — id, nome, valor_centavos (fatura nasce 0), vencimento, tipo (rótulo), paga (0/1), caixinha_paga_id, tipo_conta (`simples`/`fatura`), arquivada (0/1), user_id
- **`recorrentes`** (assinaturas) — id, nome, valor_centavos, dia_vencimento, tipo, conta_fatura_id (FK→contas fatura, ou NULL=avulsa), user_id
- **`fatura_itens`** — id, conta_id, descricao, valor_centavos, data, user_id
- **`categorias`** — id, nome, user_id (semeadas por usuário)
- **`regras_salario`** — id, gatilho, modo (`percentual`/`fixo`), valor, caixinha_id, user_id
- **`entradas_recorrentes`** (renda automática, Etapa 26) — id, nome, valor_centavos, dia, user_id
- **`config`** — (**user_id, chave**) PK composta, valor. Chaves: `categorias_iniciadas`, `wrapped_visto_ate`. *(`senha_hash` foi descontinuado.)*

**Criação/migração:** no **Postgres** o `criar_tabelas()` roda a `DDL_POSTGRES` (`CREATE TABLE IF NOT EXISTS` completo, já com `user_id` + índices) no startup — tabela nova nasce no deploy. No **SQLite**, `migrar()` faz `ALTER TABLE ADD COLUMN` idempotente.

## 5. Migração de dados (SQLite → Supabase)

`migrar_para_supabase.py <SEU_UUID> [financeiro.db]`: abre o SQLite **só-leitura**, cria o schema no Postgres, **LIMPA** o destino e copia tudo **carimbando `user_id`** em cada linha; descarta a linha `senha_hash`; acerta as sequences. Lê a conexão do `.env`.

## 6. Regras de negócio (cálculos)

**Fonte única = os lançamentos.** Saldos nunca são guardados; são somados.

- **Saldo de caixinha** (`saldo_da_caixinha`): `SUM(alocacao+rendimento) − SUM(pagamento)`.
- **Saldo livre** (`calcular_saldo_livre` / `/saldo-livre`): `SUM(entrada) − SUM(alocacao) − SUM(saida_livre)`. Rendimento não entra.
- **"Guardado em caixinhas"** (card): **soma dos saldos atuais** de todas as caixinhas — cai quando você gasta de uma (Etapa 32).
- **"Entradas do mês"** (card): entradas **só do mês corrente** (filtrado por data — Etapa 27).

**Trava de saldo (Etapa 24):** `criar_lancamento` barra `alocacao`/`saida_livre` acima do saldo livre e `pagamento` acima do saldo da caixinha (ou sem caixinha). `entrada`/`rendimento` não travam.

**Tipos de lançamento:** `entrada` (de fora, dispara regras de salário) · `alocacao` (guardar) · `pagamento` (gastar de caixinha / pagar conta / saída de transferência) · `saida_livre` (gasto do livre) · `rendimento` (juros/CDI: entra na caixinha, não conta como entrada).

**Regras de salário (E4):** ao criar `entrada`, `aplicar_regras_salario` acha regras com `gatilho`==descrição (case-insensitive) e cria `alocacao` automática (% ou fixo).

**Entradas recorrentes (Etapa 26):** `gerar_entradas_recorrentes` (chamado no load) cria a `entrada` da renda cujo dia já chegou (1×/mês, dedup por nome+mês) e **dispara as regras de salário** — se o nome bater com um gatilho, distribui sozinho.

**Transferência / Pagar conta / Fatura / Arquivar:** como antes. **Recorrentes de despesa** (`gerar_recorrentes_do_mes`, no GET /contas): vinculada a fatura válida → vira item da fatura (dedup nome+mês); senão conta avulsa (dedup nome+vencimento). **Ao desvincular/trocar de fatura (Etapa 29): remove o item do mês da fatura antiga** (senão duplicava a cobrança).

**Importar extrato (E3 + Etapa 27):** `_data_iso` cobre vários formatos (ISO c/ hora, dd-mm-aaaa, dd.mm.aaaa, aaaa/mm/dd, mês por extenso pt). O front filtra por **mês** (padrão: mês atual) pra não puxar o ano todo.

## 7. Referência de rotas

> Rotas de dados exigem `Authorization: Bearer <token>` (Supabase) e são **isoladas por `user_id`**. Valores em `valor_centavos`.

**Lançamentos:** `POST /lancamentos` · `GET /lancamentos` · `DELETE /lancamentos/{id}` · `GET /saldo-livre`
**Caixinhas:** `POST /caixinhas` · `GET /caixinhas` · `POST /caixinhas/{id}/meta` · `POST /caixinhas/{id}/mover` · `DELETE /caixinhas/{id}` · `POST /transferir`
**Contas:** `POST/GET /contas` · `PUT/DELETE /contas/{id}` · `POST /contas/{id}/pagar` · `.../desfazer-pagamento` · `GET /contas/arquivadas` · `.../arquivar` · `.../desarquivar` · `POST /contas/arquivar-antigas` · `GET/POST /contas/{id}/itens` · `DELETE /contas/{id}/itens/{item_id}`

## 8. Front-end e responsividade

- **3 arquivos:** `index.html` (estrutura), `styles.css` (tema escuro roxo + fonte Inter), `app.js` (lógica). Servidos por rotas próprias.
- **Login** Supabase (e-mail/senha), token no `localStorage`. **8 telas** no menu (Visão geral, Caixinhas, Dívidas, Histórico, Análise, Categorias, Regras, Importar).
- **Modais próprios (não nativos):** confirmação (`confirmar()`) e **formulário** (`abrirFormModal()` — editar dívida, meta) no lugar de `confirm()`/`prompt()`. **Popover** estilizado no hover do calendário.
- **Entradas automáticas** ficam na tela **Regras**. **OCR** ("Ler conta por foto"): o painel é **escondido** quando `/ocr-status` diz que o servidor não tem Tesseract.
- **Responsividade (Etapa 30):** `#cal-widget` capado em 340px (célula não fica gigante em tela larga/zoom baixo); `.principal` capado em 1600px; media queries em 1000/720px (empilha painéis, sidebar vira ícones). Testado 380–2400px sem overflow horizontal.

## 9. Deploy (Render) e segurança

**Variáveis de ambiente no Render:** `PGHOST` (Session Pooler `aws-0-sa-east-1.pooler.supabase.com`), `PGPORT=5432`, `PGDATABASE=postgres`, `PGUSER=postgres.<ref>`, `PGPASSWORD` (secreta), `PGSSLMODE=require`, e **`SUPABASE_URL`** (necessária pro JWKS/login). Opcionais: `SUPABASE_PUBLISHABLE_KEY`, `SUPABASE_JWT_SECRET`.

- ⚠ A **conexão direta** `db.<ref>.supabase.co` é **IPv6-only** e não resolve em rede IPv4 — usar sempre o **Session Pooler** (IPv4).
- **Segredos** nunca no git: `.env` e `*.local.md` no `.gitignore`. As chaves públicas (URL, publishable) podem ficar no front.

**Dívidas técnicas conhecidas:** sem rate-limiting no login (o Supabase tem o dele); front usa muito `innerHTML` (XSS — nomes passam por validação no back, mas atenção); "desfazer pagamento" é heurística (caixinha+valor); virada automática de fatura por mês não feita; OCR no Render exige Docker (Tesseract) — hoje degrada escondendo o painel.
